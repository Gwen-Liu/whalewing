# 代码审查

## 定范围

- **审什么**：明确的改动范围，例如两个提交之间（`git diff <起点>...HEAD`）、未提交的工作区改动，或员工指定的文件。起点不清楚就问；范围为空或提交号无效先说明，不做空审查。
- **对照什么**：
  - 需求：任务原文、需求文档、缺陷描述或实施计划。找不到就问员工；确实没有时，需求线写“无需求可对照”，不自己编一份。
  - 规范：工程的规则文件（如 `AGENTS.md`、`CONTRIBUTING.md`、代码规范文档、lint 配置）和相邻代码的既有写法。
- **只读**：审查不修改工作区、暂存区和当前分支；要看别的版本就检出到临时目录。lint、格式化、类型检查已经管住的问题不重复报。

## 两条线分开审

一项改动可能完全符合规范却做错了事，也可能做对了事却破坏了工程约定。两条线分开写结论，不合并、不互相抵消。

**需求线**

- 要求做的有没有缺失或只做了一半；
- 做了需求没要的：范围蔓延、为想象中的将来加的参数和抽象；
- 看起来实现了，但实现得不对；
- 需求没写到的情况，按正常使用者的合理预期判断：需求没写不等于允许出错。

**规范线**

- 违反工程文档写明的规则：引用规则的出处；
- 正确性：边界条件、空值、错误处理（吞掉异常、失败不可见）、并发和取消、资源释放；
- 安全：注入、密钥写进代码、缺少权限检查、不可信输入直接拼进命令或 SQL；
- 测试：测的是真实行为还是只测了模拟对象；新行为和修过的缺陷有没有对应测试；
- 可维护性（判断题，不是硬违规；工程规范与之冲突时以工程为准）：命名说不清用途、重复逻辑、一个改动要散改很多文件、一个文件因为几件无关的事被改、只转手不干活的中间层、只为想象需求存在的抽象、注释复述代码或与代码不符、留下调试输出和注释掉的旧代码。

改动太大读不完时分几轮读，并在结论里说明；没读到的代码不评价。

## 写结论

每个问题写：位置（`文件:行`）、哪里不对、为什么要紧、怎么改（不明显时）。按实际严重程度分级：

- **必须修**：缺陷、安全问题、数据丢失风险、功能不可用；
- **应该修**：结构问题、需求缺口、错误处理不当、缺测试；
- **可以改**：风格、小优化、文档润色。

不把挑剔说成必须修。先写做得好的地方，具体到位置；准确的肯定能让作者更相信其余意见。列出考虑过、但判定超出本次范围的事，每条一行写原因，不悄悄丢掉。最后给明确结论：可以合并、修完再合并或不能合并，附一两句理由。没看过的代码不说“看起来不错”。

## 独立审查

重要改动请没参与编写的人审。用原生子代理时，只交给它改动范围、需求出处和规范文件清单，不交作者的对话过程；审查者自己读完，不再委派别人。作者自审不冒称独立审查。

## 收到审查意见时

1. 读完全部意见再动手。有看不懂的条目先问清，条目之间可能相关，不先做看得懂的那部分。
2. 每条先对照代码核实：在这个工程里技术上成立吗？会不会弄坏现有功能？现在这样写有没有原因（兼容、平台、员工之前的决定）？
3. 意见不成立就用证据说明（代码、测试、文档）；与员工之前的决定冲突时先和员工确认。建议把某个功能“做完整”时，先查有没有地方在用，没人用就提议删掉，而不是做完整。
4. 按顺序改：先阻断和安全问题，再简单修正，最后复杂改动；每改一条测一条，最后跑完整测试。
5. 回复只说改了什么、在哪里，不写客套和表态。之前反驳错了，直接写核实结果并改正。

## 退出

审查方交付：审查范围、对照的需求和规范、分级问题清单、超出范围清单和结论。作者方交付：逐条处理结果（已改、不改及理由、待员工决定）和测试结果。完成本次审查或本轮修改即退出，不借审查重写代码。
